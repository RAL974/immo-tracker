## Pseudonymisation d'employes.json (fait, fin août 2026)

Détail technique complet : `01_ARCHITECTURE_TECHNIQUE.md` § Pseudonymisation d'employes.json. Raisonnement et décisions : `04_HISTORIQUE_DECISIONS.md`.

**Statut** : les deux étapes sont faites et déployées. Étape 1 (endpoint `?noms_employes=1` + cache navigateur) vérifiée en conditions réelles contre l'environnement de recette avant l'étape 2. Étape 2 (retrait du nom de `?employes=1`, bascule d'`employes.json` en version codes-only) faite sur feu vert explicite de William, avec garde-fou anti-régression dédié (`tests/security.employes-sans-nom.test.js`).

**Découverte faite pendant l'analyse d'impact, à ne pas perdre** : `getNomResolver()` (worker.js) attache un nom résolu à de nombreux autres endpoints publics non authentifiés au-delà de `?employes=1` — `?dashboard=1` en premier lieu (jusqu'à 5000 mouvements, chacun avec `nom_employe`, probablement le plus gros volume de données personnelles exposées de tout le Worker), plus les réservations, campagnes d'inventaire, dotations EPI. Décision explicite avec William : **rester borné à `employes.json`/`?employes=1` pour ce chantier** — fermer toute la propagation via `getNomResolver()` est une refonte bien plus large (re-router l'endpoint le plus consulté de l'app), à traiter dans une session dédiée séparée si la direction le souhaite. Voir "Reste à faire" ci-dessous.

## Politique de mot de passe et persistance du verrou anti brute-force (10 août 2026)

Détail technique complet et raisonnement : `04_HISTORIQUE_DECISIONS.md`. Solde les points 2 et 3 du "reste à faire" de l'audit du 9-10 août 2026 (ci-dessous).

**Politique de mot de passe (`PASSWORD_MIN_LENGTH`, worker.js)** : minimum relevé de 4 à 8 caractères. S'applique uniquement à `set_password` (création ou changement) — jamais à `verify_password`, qui ne vérifie que le hash, jamais la longueur. **Aucun compte existant n'est cassé** : un mot de passe créé avant ce durcissement avec 4-7 caractères reste utilisable tel quel à la connexion, sans migration ni renouvellement forcé. Message d'erreur dédié côté Worker (`mot_de_passe_trop_court` + `min_length`) et côté dashboard (texte explicite, plus le seuil client-side déjà présent relevé à 8). Testé : `tests/worker.password-policy.test.js` (refus à 7, acceptation à 8, ancien compte à 4 caractères toujours connectable — avec un vrai hash PBKDF2 recalculé dans le test, pas un mock arbitraire).

**Option non retenue à ce stade, proposée à William** : un indicateur "mot de passe faible, à renouveler" pour les comptes dont le hash a été créé avant ce durcissement — techniquement simple (comparer la date de dernière modification du hash, si SharePoint la conserve, à la date de ce déploiement) mais pas implémenté : nécessiterait de trancher où l'afficher (fiche employé ? bandeau à la connexion ?) et si le renouvellement doit être seulement suggéré ou forcé. À cadrer avec William si le besoin se confirme.

**Persistance du verrou anti brute-force via Cloudflare KV** : `LOGIN_ATTEMPTS` (Map en mémoire, inchangée) reste le mécanisme par défaut et le repli automatique. Un binding KV optionnel `LOGIN_ATTEMPTS_KV`, s'il est provisionné, rend ce même compteur persistant et partagé entre tous les nœuds edge Cloudflare — scopé **exclusivement à `verify_password`** (ni `set_password`, qui reste memory-only par choix explicite pour ne pas ajouter de latence sur un chemin peu fréquent, ni aucune autre action) pour ne jamais ralentir une connexion normale. `reset_password` (admin) purge désormais aussi la clé KV en plus de la mémoire, pour préserver la garantie déjà existante ("un admin qui réinitialise lève le verrou").

- **Repli gracieux total, vérifié par test** : si le binding est absent (`loginAttemptsKv()` renvoie `null`) ou qu'un appel KV échoue (quota dépassé, incident réseau — `try/catch` systématique), le Worker retombe silencieusement sur le comportement actuel (mémoire), sans jamais faire échouer une connexion à cause de KV.
- **Limites du plan gratuit Cloudflare KV vérifiées le 10 août 2026** (`developers.cloudflare.com/kv/platform/limits/`) : 100 000 lectures/jour, 1 000 écritures/jour (clés différentes), 1 écriture/seconde sur une même clé, 1 Go de stockage par namespace, 1 000 namespaces par compte. **Très largement suffisant pour ce projet** (~97 comptes, quelques connexions par jour chacun) : une lecture KV par tentative `verify_password` réelle (la sonde `__probe__` du dashboard, appelée bien plus souvent, ne déclenche aucune lecture KV — elle court-circuite avant), une écriture uniquement sur échec. Même un brute-force soutenu contre un seul code reste naturellement bridé par le verrou lui-même (aucune nouvelle tentative pendant les 30s/5min/15min de blocage), donc pas de risque réaliste de dépasser 1 000 écritures/jour.
- **✅ Activé le 10 août 2026.** William a créé le namespace `immo_tracker_login_attempts` (Cloudflare dashboard → Storage & databases → Workers KV → Create Instance) et son ID a été renseigné dans `wrangler.toml` (`kv_namespaces`, binding `LOGIN_ATTEMPTS_KV`, ressource `immo-proxy` uniquement). Le prochain déploiement Git active la persistance sans autre changement de code — `worker.js` détecte le binding automatiquement au runtime (`loginAttemptsKv()`).
  - **Pourquoi le binding n'a pas été ajouté directement avec un ID dès l'écriture du code** : contrairement aux secrets (`CLIENT_SECRET_ENV`/`SESSION_SECRET_ENV`, absents → échec explicite mais déploiement toujours réussi), un `kv_namespaces` déclaré dans `wrangler.toml` avec un ID de namespace invalide ou inexistant aurait fait **échouer le déploiement entier du Worker** (pas seulement cette fonctionnalité) — `wrangler deploy` valide l'existence du namespace auprès de Cloudflare à chaque déploiement. D'où le choix initial d'un bloc commenté, activé seulement une fois l'ID réel obtenu de William.
- **Environnement de recette (`immo-proxy-staging`)** : non concerné à ce stade — le binding n'est actif que pour la ressource de production (`immo-proxy`). À dupliquer sous `[env.staging]` si William souhaite aussi tester la persistance KV côté recette (créer un second namespace dédié, jamais partager le même entre prod et recette).
- Testé : `tests/worker.rate-limit.test.js` — paliers via KV, persistance simulée entre deux "isolates" (même mock KV réutilisé à travers deux rechargements du Worker, chacun réinitialisant la mémoire), repli gracieux si KV échoue, scope limité à `verify_password` (un compteur d'appels KV reste à 0 pendant un brute-force simulé sur `set_password`), et purge KV par `reset_password`.

## Limites assumées de la réécriture d'historique

La réécriture (`git filter-repo --path materiel_it_catalogue.json --invert-paths`) supprime le fichier de tous les commits du dépôt réécrit et remplace tous les SHA en aval. Vérifié après le force-push :
- **`git log --all`/`git branch --contains` sur le dépôt** : le commit `b48a4f7` n'est plus atteignable depuis aucune branche ou tag distant — un `git clone` ou `git pull` normal ne le récupère plus.
- **⚠️ Constaté, pas seulement théorique : GitHub sert toujours la page du commit par son SHA direct** (`github.com/RAL974/immo-tracker/commit/b48a4f7`), avec la mention "This commit does not belong to any branch on this repository, and may belong to a fork outside of the repository." — comportement GitHub connu après une réécriture d'historique (rétention interne le temps de leur propre nettoyage, pas instantané, parfois plusieurs semaines). Le fichier reste donc potentiellement récupérable via cette URL directe tant que GitHub n'a pas purgé ses objets orphelins. **Action recommandée à William** : ouvrir une demande auprès du support GitHub (formulaire dédié "supprimer des données sensibles", accessible depuis les paramètres de sécurité du dépôt) pour forcer la purge immédiate de ce commit précis — je ne peux pas soumettre cette demande à sa place (nécessite son compte GitHub).
- Toute copie déjà clonée du dépôt (un autre poste, un fork, un mirroir) conserverait l'ancien historique intact tant qu'elle n'est pas elle-même réécrite ou resynchronisée depuis zéro. Aucun autre clone connu à ce jour (dépôt à usage interne, un seul mainteneur) — mais non vérifiable à 100% depuis ce dépôt.
- **La réécriture ne remplace pas la rotation des codes eux-mêmes** (voir ci-dessous) : elle réduit la surface de découverte future, elle ne rend pas les anciens PIN/PUK/RIO à nouveau secrets — d'autant plus tant que la page GitHub du commit reste servie.

## Comment vérifier que ça tient dans le temps

`npm run verify` (`npm run check` + `npm test`) avant chaque push — bloqué par le hook `pre-push` si un test échoue. Les tests de sécurité vivent dans `tests/security.*.test.js` et `tests/worker.rate-limit.test.js`/`tests/worker.password-policy.test.js`/`tests/worker.security-headers.test.js` : ils échoueront explicitement si une régression réintroduit un des problèmes corrigés ici (action gated oubliée, `is_reset` réintroduit, CORS rouvert au wildcard, endpoint Matériel IT dégatté, verrou KV qui fuit sur `set_password`, règle des 8 caractères oubliée...). Toute nouvelle action Worker sensible doit être ajoutée à `GATED_ACTIONS` **et** à `requireAdmin`/`requireGarant` — sinon `security.gated-actions.test.js` le signale immédiatement.
